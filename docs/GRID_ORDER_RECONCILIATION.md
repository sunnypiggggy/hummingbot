# Grid 订单核对与不可成交库存

Grid 重建不能只依赖运行 JSON 中的订单 ID。策略合并自身活动订单和连接器订单，通过当前实例 SQLite 的 `Order` 记录校验配置、策略、交易对、订单类型和交易所 ID，找回丢失的普通 Maker 订单跟踪。找回跟踪不重复记账；真实成交仍通过成交事件处理。

## 重建边界

- 单对刷新只撤该交易对的已证明归属订单。未知订单保留待核实，保护性退出订单单独处理。
- 连接器仍有订单时不能删除其归属 ID。交易所仍有订单、证据陈旧或证据早于撤单请求时，不提交新一代网格。
- Guard 复用动态预检的真实交易所查询，原子发布账户绑定的 `grid_exchange_order_snapshot.json`。证据最多有效 30 秒；查询失败不伪造空订单列表。
- 全部核对通过才能重建；实际挂单 ID 与账本一致后才能发送故障恢复通知。
- 核对失败限制普通订单重建，不清仓、不锁存、不覆盖 v22 或其他门。正常 Risk-Off 空网格不作为执行异常。

## 持仓保护与 dust

48 小时额外库存保护先按交易所数量步长、最小数量及最小金额判断可成交性，再撤普通订单。不可成交残余持久化到 `inventory_exit_dust`，不停止普通网格、不产生卖单。数量或过滤器变化重新核验；单纯价格变化但仍不可成交不重复记录事件。重新可成交时按原保护规则执行。

## 当前异常及频道

Guard 的持久化 `RuntimeErrorChannel` 是网格持续执行故障的唯一通知来源，Report 将活动故障提供给管理 Bot。页面展示交易对、中文原因、持续时间、残留挂单和解除条件。恢复必须有新网格和交易所证据，不因风险门关闭、日志暂时安静或进程重启而宣称恢复。

## 例行刷新与模型更新的区别

两小时例行刷新使用逐交易对异步撤单和核对。等待撤单后的交易所证据时保留原网格参数、库存及撤单游标，前30秒不作为故障；持续等待由Guard报告网格执行异常，不清仓、不锁存。订单重建事件不再发送“参数/模型更新失败”，真正候选训练、审批和激活通知保持不变。

```powershell
python -m pytest test/test_grid_guard_shadow.py test/test_grid_execution_monitor.py test/test_grid_live_safety.py test/test_telegram_notifications.py test/test_trading_management_bot.py -q
```

在含完整 Hummingbot/Cython 的隔离镜像中运行 `test/test_grid_live_runtime_risk.py`，不挂载生产状态、密钥或 Docker socket，禁止公网访问。覆盖真实 SQLite 的丢失 ID、部分成交、撤单延迟、交易所与连接器视图不同步、陈旧证据、重启、未知订单和 dust。发布后仍需核验实际交易所订单、归属数量、加载版本及至少 15 分钟运行情况，单元测试不代替实盘验收。

## 发布依赖

Grid scheduler 的 `ensure_staging()` 会在每轮协调中将镜像内策略复制到共享 scripts 目录。策略发布必须同步 scheduler 内的策略副本，否则挂载新文件会被旧镜像覆盖。定向发布时以实际运行镜像为基底，仅替换本次文件，并验证其余调度、模型与参数逻辑未变；不要将尚未运行的同名镜像标签当作基底。最终同时核对 scheduler 副本、共享文件、Grid 进程加载哈希，不能仅以 `docker start` 成功判定加载完成。
